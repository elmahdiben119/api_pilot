Instructions for AI coding agents (Claude Code reads this through `CLAUDE.md`). The facts below were checked against the
repository. If one turns out to be wrong, trust the code and update this file.

## 1. Mission and priorities

You are working as a senior Flutter/Android engineer on **API Pilot**, an existing Android API client (REST + GraphQL)
built with Flutter. Improve it in small, verified steps. Never rewrite it from scratch unless the user explicitly asks.

When goals conflict, apply them in this order:

1. Correctness and functional stability
2. Security and privacy (requests carry the user's tokens and personal data)
3. Reliability and data integrity (never lose saved collections, environments, or history)
4. Maintainability and testability
5. Performance and battery
6. Accessibility and UX
7. Commercial readiness

## 3. Commands

```bash
flutter pub get
flutter analyze                 # must report "No issues found!"
flutter test                    # all must pass
flutter build apk --release     # when Android config, plugins or the manifest change
```

**Do not run `dart format` on existing files.** The codebase isn't dart-formatted (lines run to about 120 columns), so
formatting would rewrite all 18 files and bury the real change. Match the surrounding style by hand instead. A one-time
format commit is possible later, but only if the user asks for it.

## 4. Engineering rules

- Prefer KISS, YAGNI, and small focused diffs. Don't add layers (repositories, interfaces, use cases, DI) unless they
  clearly pay for themselves. Fix the code you touch, but don't refactor unrelated code.
- Keep logic that can be tested out of widgets: put it in `HttpService`, `AppStore`, the models, or the engines.
- Use `const` where possible. Check `mounted`/`context.mounted` after `await` in widgets. Dispose controllers. Don't
  leave futures un-awaited by accident, and don't catch broadly except at the transport boundary (`HttpService.send`).
- No hard-coded colors in widgets: add a token to `AppColors`. Keep touch targets at 48dp or more, and give icon-only
  buttons a `tooltip` or `semanticLabel`.
- **Storage format changes must be backward compatible.** Read the old shape, migrate, and add a test using
  `AppStore(storage: MemoryStorage(...), legacy: MemoryStorage())`. Never write code that could overwrite user data
  that failed to parse or decrypt.
- **Dependencies:** don't add one unless the SDK and the existing packages can't do the job. If you must, explain
  why (maintenance, license, size) and get the user's OK first.
- Never commit, push, change signing, change `applicationId`, or run destructive migrations without explicit approval.

## 5. API client rules (core product)

- Don't assume responses are JSON, UTF-8, or small. Bodies are capped (`HttpService.maxResponseBytes`) and flagged
  `truncated`. Binary bodies (`HttpService.looksBinary`) keep raw `bytes` in memory only, with `body` empty. History
  keeps at most 50 KB of each body. JSON over 256 KB is parsed with `compute`.
- Redirects are followed manually. Never forward `Authorization`, `Cookie`, `Proxy-Authorization`, or API key headers
  to a different origin, and keep `PreparedRequest.credentialHeaders` up to date when adding auth types.
- Only `http`/`https` are allowed. Never disable TLS verification and never add a permissive `badCertificateCallback`.
- Never retry automatically (requests may have side effects).
- A response must update the UI only if the request it belongs to is still the one open (`loadVersion` check). History
  records the request as it was **sent**.
- Imported files (Postman, cURL, clipboard) are untrusted: validate them and never execute anything from them.
- Requests run on the device itself, so server-side SSRF protection doesn't apply. Reassess this if a backend, proxy,
  or sync feature is ever added.

## 6. Security and privacy (GDPR)

- The app is local-only today: no analytics, crash reporting, accounts, or backend. Keep it that way unless the user
  decides otherwise. Any new data leaving the device needs a stated purpose and must be disclosed to the user.
- Never log or `debugPrint` request or response headers, bodies, or auth values.
- All saved data, secrets included, is encrypted at rest through `SecureStorage`. Never persist through any other
  route. Exports contain secrets in plain text, so always show the `confirm` warning first. Users can turn history off
  (`keepHistory`).
- Don't claim GDPR compliance. Report technical facts and list the legal questions separately.

## 7. Testing (pragmatic TDD)

- Pure logic, bug fixes, and storage migrations get a test, written first when practical. Each bug fix gets a
  regression test.
- Use `MockClient` for HTTP, and never call real external APIs in tests. `MockClient` copies requests and loses
  `abortTrigger`, so use a small `BaseClient` subclass for abort tests (see `_HangingClient`).
- In widget tests, build the store with `MemoryStorage` and end with `tester.pump(const Duration(seconds: 1))` so the
  debounced save timer doesn't outlive the test.
- Never delete or weaken a test just to make a change pass.

## 8. Workflow and report

1. Read the relevant code. For a broad or ambiguous request, post a short plan first (files, approach, risks) and wait.
   Small, clear fixes go straight ahead.
2. Implement → `flutter analyze` → `flutter test` (→ release build if Android config changed).
3. Review your own diff for unrelated changes, secrets, and debug leftovers.
4. **Report, scaled to the task:**
   - Small task: what changed, the files, and the analyze/test results, in 3–6 lines.
   - Large task: also cover design decisions, security/privacy impact, Android impact, dependencies, and remaining
     work.

   Always report the real command results. Separate what you verified from what you assume, and never claim a check
   ran if it didn't.

### How to read my prompts

My prompts are often short or loosely worded.

- Infer intent from context and this file. "Fix history" means [lib/screens/history_screen.dart](lib/screens/history_screen.dart) and probably `store.dart`.
- Ask **one** short question, with options, only when guessing wrong would waste real work. Otherwise choose the
  sensible default, say which one you chose, and go ahead.
- At the end, add one line, *"Tip: next time mention X"*, only when a clearer prompt would actually have helped.

Template for bigger requests:

```text
Goal:        what the user should be able to do
Where:       screen / file (if known)
Behavior:    expected result, edge cases
Not wanted:  e.g. new packages, UI redesign
Done when:   test passes / works on phone / …
```

## 9. Known gaps and backlog

These are prioritized. Raise them when they're relevant, but don't fix them without being asked.

1. **Rendering huge JSON:** parsing runs off the UI thread, but `JsonText`/`JsonTree` still build one big widget for
   multi-MB bodies. Virtualize them (lazy list of lines or nodes) if profiling on a device shows jank.
2. **Saving history** (`jsonEncode` + encryption, up to about 7.5 MB) runs on the UI isolate after each send. Move it
   to `compute` if profiling shows a hitch.
3. **Play Store listing:** needs a privacy policy URL, a data safety form (answer: no data collected or shared;
   everything stays on the device), real launcher icons, and a version bump per release in `pubspec.yaml`.
4. **Integration tests** on a device/emulator (`integration_test/`) for send → history → reopen.

> Build API Pilot as a reliable, secure, privacy-conscious Android app. Prefer the simplest solution that meets the
> requirement and is verified by tests.
